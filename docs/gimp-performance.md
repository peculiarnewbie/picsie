# GIMP interaction measurements

Measured 2026-09-30 using packaged GIMP 3.2.6 and the current Picsie GPUI release
(`d8a459e`). This is a functionality/performance investigation; GIMP remains
explicitly excluded as a UX reference. The external source checkout was not built.

These are baseline measurements. Subsequent code experiments and verified real-GPU
results are in [the experiment report](desktop-gimp-experiments.md), including
the subsequent X11 frame-wakeup comparison and the
[2026-10-01 feature/scale audit](desktop-gimp-experiments.md#fourth-pass-feature-polish-and-document-scale).
The [expanded twelve-behavior comparison](desktop-gimp-experiments.md#fifth-pass-twelve-behavior-performance-coverage)
also measures fill, clear, retained crop, image resize, brush and eraser, with
native stroke observations and explicit output-quality checks. The
[sixth pass](desktop-gimp-experiments.md#sixth-pass-immutable-raster-and-bounded-pixel-work)
integrates and repeats the image-painting, selected-pixel and bounded-feather
optimizations. Further repeated performance testing is required for unmeasured
features and combinations; the twelve-family inventory is not complete coverage.
The [seventh pass](desktop-gimp-experiments.md#seventh-pass-layer-ordering-navigation-and-resize-stress)
records the subsequent 50–1,000-layer CPU ordering/navigation breadth, repeated
resize controls, native stress interactions and clipping/sampling diagnostics.
The [requested stress matrix](desktop-gimp-experiments.md#requested-stress-matrix-layer-ordering-navigation-and-resize)
remains the broader coverage target; its untested variants are tracked explicitly.
Do not substitute these original
software-rendering numbers for the newer hardware cohorts.

## Results

Latency and visible-interval percentiles pool all measured samples. Update rates
are medians of the three run rates. The faster drag is the main throughput result.

| Measurement | GIMP 3.2.6 | Picsie editable demo | Picsie raster control |
| --- | ---: | ---: | ---: |
| Nudge → visible change, median | **33.9 ms** | 75.5 ms | 78.4 ms |
| Nudge → visible change, p95 | **37.7 ms** | 79.0 ms | 131.6 ms |
| Faster drag, visible updates/sec | **41.0** | 20.7 | 21.0 |
| Faster drag, median visible interval | **18.2 ms** | 47.8 ms | 47.7 ms |
| Faster drag, p95 visible interval | **42.6 ms** | 52.0 ms | 52.3 ms |
| Original slower drag, visible updates/sec | **31.2** | 20.7 | 19.0 |
| Faster drag CPU, 100% = one logical core | **178%** | 568% | 570% |

GIMP's faster-drag run rates were 39.2–43.2 updates/sec, compared with 20.2–20.7 for
the editable Picsie demo and 20.2–21.0 for its raster control. GIMP's nudge medians
were 33.86–33.90 ms, versus 75.52–75.71 ms for the editable Picsie demo. The raster
control had more latency variation: run medians 76.1, 119.6, and 75.9 ms. Its pooled
p95 includes the slow second run; no samples were discarded from measured runs.
These short repeats are not statistical confidence intervals.

On this workload, GIMP delivered approximately twice as many visible changes with
roughly half Picsie's input latency. Its median update interval approaches a 60 Hz
cadence, but its p95 interval is 42.6 ms. Only 50.3% of observed faster-drag intervals
were at most 20 ms. **This run does not demonstrate sustained 60 fps at p95, or
p95 input-to-visible latency at most 20 ms, for GIMP.** Neither target is achieved
by Picsie here either.

Rasterizing Picsie's document does not close the observed throughput gap. This
supports investigating how much work each update performs and how frames reach
the screen. It does not isolate savings to GEGL caching, GPUI, transport, or a
particular rendering stage. GIMP's tile/region caching is a source-inspection
finding, not a component cost measured by this application benchmark.

The subsequent [rendering analysis](gimp-rendering-analysis.md) traces GIMP's
actual layer-move path, compares Picsie's caches and publication costs, and
records separate diagnostic timing runs. Those traced runs are not pooled into
the untraced results above. Subsequent changes to Picsie and repeated comparisons
are recorded in [the codebase experiment report](desktop-gimp-experiments.md).

## Workload and method

- Same AMD Ryzen 5 5600U Linux host and X11/Xvfb environment as the earlier
  [Picsie optimization measurements](desktop-optimization.md).
- Six-layer 1200×800 Color studies document, 936×734 canvas, 71.333333% zoom.
- GIMP loads an OpenRaster package containing the layer PNGs generated by the
  existing Rust `.comp` exporter, with their original offsets and blend modes.
  Electric blue is the selected layer. Text, shapes, and the gradient are
  rasterized for GIMP. GIMP's blending/color conversion can differ from Picsie;
  this is not a pixel-parity claim.
- Picsie runs twice: its original editable demo, and a control using the same
  exported/reimported raster layers. No application code or tracing is enabled.
- GIMP's docks are hidden and its window is 970×834 to provide the same visible
  canvas size as Picsie's 1280×860 window. These are benchmark setup choices,
  not proposed Picsie workflows.
- External XTest input and `XGetImage` observations of the first fully blue pixel
  at y=550, reusing the previous desktop benchmark's detector and resource sampler.
  Requested polling interval is 4 ms. This ends at the virtual framebuffer,
  excluding a physical GPU, desktop compositor, display scanout, and input-device
  hardware delay. GIMP uses its GTK/Cairo display path; Picsie uses software Vulkan.
- One complete discarded warm-up run per application, followed by three measured
  launches in rotating order. No concurrent builds or other editor instances.

Each launch measures 28 alternating Shift+Right/Left nudges, discarding the first
four. The pooled latency summary therefore contains 72 measured inputs per app.
GIMP's native shortcut moves approximately 35 document pixels / 25 screen pixels
at this zoom; Picsie's moves 10 document pixels / approximately 7 screen pixels.
Both are single key gestures. Expected displacement and return to the starting
position are asserted. These are comparable shortcut interactions, not identical
command semantics.

Two four-second out-and-back drags supply 480 motion events each at a requested
120 Hz. Excursions are 120 and 240 screen pixels. The former reproduces the earlier
test; its 60 pixels/sec movement limits how many distinct integer edge positions
can be observed. The latter moves at 120 pixels/sec, allowing the detector to
distinguish 60 visible updates/sec from faster rates. Each drag must reach its
expected excursion and return to its initial edge. Visible intervals are the gaps
between observed position changes, not internal draw calls or unchanged refreshes.

GIMP's isolated configuration disables its welcome/update prompts and enables
`devices-share-tool`, because the synthetic input clients otherwise cause GIMP to
restore different tools mid-test. No rendering-quality, CPU acceleration, GEGL
thread-count, or tile-cache tuning is applied. The failed setup pilots are excluded.

All 216 measured nudges and all 18 measured drags passed the movement assertions.
The saved starting and returned canvases and GIMP's selected-tool setup screenshots
were inspected. The architecture guard, Python syntax/CLI checks, and a fresh
Rust-generated six-layer fixture preparation also passed.

Measured faster-drag motion spacing had per-run medians 8.37–8.44 ms, and observation
spacing had per-run medians 4.34–4.48 ms. The approximately 4 ms observation interval
adds quantization and delay; it cannot simply be subtracted from the percentiles.
The two applications use different controls and display backends, and GIMP's docks
are hidden to match the canvas. This compares these application configurations,
not identical UI rendering workloads.

## Reproduction and evidence

The GIMP package and missing runtime dependencies are extracted under ignored
`artifacts/gimp-performance/runtime`; no system package or user GIMP configuration
is changed. GIMP's data/plugin/typelib/GEGL/babl paths point at that prefix. The
runtime includes babl SIMD extensions. Package versions, download URLs, and SHA-256
hashes are retained in `artifacts/gimp-performance/packages.json`.

After staging that runtime and building the existing native addon and release UI:

```sh
python3 scripts/compare-gimp-performance.py --prepare-fixture
```

The driver accepts alternate `--runtime`, `--picsie`, `--tools`, `--fixture`,
`--output`, `--display`, `--apps`, and `--trials` arguments. Fixture preparation calls
the Rust addon to generate layer PNGs and projects, then packages the assets as
OpenRaster. It does not implement editor rendering in Python or JavaScript.

Evidence stays under ignored `artifacts/gimp-performance/`:

- `environment.json`: CPU/OS, Git base, fixture hashes, and runtime paths.
- `packages.json`: actual extracted packages and their hashes.
- `comparison/application-results.json`: pooled summary and complete measured runs.
- Per-run `result.json`: every nudge, drag transition, input time, and poll time.
- Per-run screenshots: selected tool, selected-layer mode, zoom, starting canvas,
  and canvas after each drag.
- `comparison/canvas-checks.json`: within-application returned-canvas comparisons.
- `comparison-run.log`: benchmark output; failed/discarded pilots live separately.

This measures layer nudges and dragging on one moderate document. It does not
establish brush latency, filter performance, large-document throughput, a universal
GIMP frame rate, or physical-display p95 performance.
